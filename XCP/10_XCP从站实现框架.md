# XCP 从站实现框架

## 典型软件分层

```text
CAN ISR / DMA
    ↓
传输适配层：收发队列、帧长度、CAN ID
    ↓
XCP 协议层：PID 分发、会话、错误响应
    ├── 内存访问适配器
    ├── DAQ 管理器
    ├── STIM 接收器
    ├── CAL/PAG 页面管理
    └── PGM 编程适配器
    ↓
应用适配层：变量快照、事件触发、参数提交
```

传输层不应决定车速或转矩的业务含义；应用层也不应直接拼 XCP PID 或修改协议状态。

## 任务和中断职责

一个可行的实时边界是：

- CAN ISR/DMA：尽快接收帧，写入环形队列，避免解析复杂命令。
- XCP 任务：解析 CTO、检查状态、调用内存/DAQ/STIM 适配器。
- 控制任务：在确定的 Event Channel 点触发 DAQ 采样或提交 STIM 快照。
- 发送任务或驱动：把响应和 DTO 交给 CAN 发送队列。

任务周期、优先级和队列深度必须结合实际 MCU、CAN 负载和控制周期确定，不能从示例直接复制。

## 一次 CTO 的处理时序

```text
CAN 接收 ISR/DMA
  -> 入队并记录时间戳
XCP 任务
  -> 取帧、检查长度和 PID
  -> 检查连接/权限/资源状态
  -> 调用内存或配置适配器
  -> 生成 RES/ERR
发送任务
  -> 申请发送邮箱
  -> 发送响应并记录结果
```

接收中断和控制任务之间应使用明确的队列或快照协议。不能让协议任务直接引用已经被 DMA 重用的接收缓冲区。

## 一次 DAQ 事件的处理时序

```text
控制任务到达事件点
  -> Xcp_DaqEvent(event_id)
  -> 读取应用稳定快照
  -> 按 ODT Entry 顺序打包
  -> 添加 PID/时间戳（如配置要求）
  -> 提交发送队列
  -> CAN 驱动发送 DTO
```

如果打包过程可能超过控制任务预算，可以使用预计算布局和双缓冲，把复杂发送动作放到较低优先级任务；但采样时刻必须先被准确捕获。

## 内存访问接口

建议把协议层和地址安全策略分开：

```c
Xcp_Status Xcp_MemoryRead(uint32_t address,
                          uint8_t extension,
                          uint8_t *buffer,
                          uint32_t length);
```

适配器应检查空指针、长度、地址段、权限、对齐和当前 ECU 状态。Flash 写入还要返回擦除忙、校验失败、掉电中断等具体原因。

## 缓冲区所有权

| 缓冲区 | 写入者 | 读取者 | 生命周期 |
| --- | --- | --- | --- |
| RX 缓冲区 | CAN ISR/DMA | XCP 任务 | 入队完成前不可复用 |
| DAQ DTO 缓冲区 | 事件处理 | CAN 驱动 | 发送完成前不可覆盖 |
| STIM 快照 | XCP 接收层 | 应用任务 | 双缓冲切换后保持稳定 |

所有权不清时，常见故障是 DTO 发送过程中内容被下一次采样覆盖，或 STIM 应用读取到半帧。

## DAQ 事件接口

应用任务不需要知道 ODT 的内部链表或 CAN ID，只提供类似下面的意图接口：

```c
void Xcp_DaqEvent(uint16_t event_id);
```

XCP 模块收到事件后，根据已激活配置读取变量、生成 DTO 并提交发送。事件接口不能长时间阻塞控制任务。

## STIM 快照接口

STIM 接收层先验证帧长度、序号、时间窗口和数据范围，再把完整数据发布给应用。应用读取的是稳定快照，而不是 CAN 接收缓冲区本身。

```text
接收缓存 -> 校验 -> 双缓冲切换 -> 应用读取
```

## 资源管理

启动 DAQ 前需要确认 ODT、发送缓存和事件绑定资源。资源不足时应返回明确错误，不应静默覆盖其他 DAQ 配置。停止或断开连接时应释放或复位运行时资源。

## 并发保护

DAQ 配置命令可能与 Event Channel 同时发生，STIM 接收也可能与控制任务并发。可采用临界区、任务通知、读写锁、双缓冲或配置到影子对象后原子切换等方式。保护范围要尽量短，不能在锁内等待总线发送。

## 断线和恢复

断线处理至少包括：

1. 停止主动 DTO 和 STIM 使用。
2. 清理未完成的块传输和发送队列。
3. 保留或清除 DAQ 配置，按项目策略决定。
4. 使临时标定参数和页面状态进入定义好的状态。
5. 重新 CONNECT 后重新检查能力，不假定旧会话仍有效。

## 代码审查重点

- 协议状态是否只由 XCP 模块修改？
- 地址访问是否经过白名单和边界检查？
- DAQ 事件是否可能与配置切换并发？
- DTO 和 STIM 缓冲区是否存在生命周期或半更新问题？
- 发送队列满时是否有统计和降级？
- Flash 写入是否有完整性校验和掉电恢复？

## 最小验证用例

1. 未 CONNECT 时发送读取命令，应得到错误响应。
2. 使用合法 RAM 地址完成 SET_MTA + UPLOAD。
3. 使用越界地址，确认没有 HardFault 且返回内存错误。
4. 配置一个 DAQ，验证事件触发、停止和重新配置。
5. 注入迟到或错误 STIM，确认算法回退策略。
6. 人为填满发送队列，确认统计、丢弃策略和恢复。
7. 中途断开连接，确认主动 DTO、STIM 和块传输状态清理。
