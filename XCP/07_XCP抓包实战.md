# XCP 抓包实战

## 准备材料

- CAN 接口和抓包工具；
- 当前 ECU 软件版本；
- 与软件匹配的 A2L；
- CAN 总线速率和 XCP ID 配置；
- 明确的测试变量和安全的 RAM 参数。

涉及写 RAM、Flash 或 Seed & Key 时，应按项目授权和测试规范操作。

## 抓包步骤

### 1. 先记录静态信息

```text
软件版本：
A2L 版本：
CAN 速率：
命令接收 ID：
响应/DAQ ID：
目标变量：
```

### 2. 识别连接阶段

观察是否依次出现 CONNECT、能力查询、状态查询和权限解锁。把每一条命令与响应配对，记录错误响应和等待时间。

### 3. 识别单次读取

重点关注：

```text
设置 MTA 地址
       ↓
UPLOAD 请求
       ↓
返回原始字节
       ↓
A2L 换算为物理值
```

### 4. 识别 DAQ

配置阶段通常会出现 DAQ List、ODT 和 ODT Entry 相关操作；启动后，ECU 应在事件周期主动发送带 DAQ PID 的 DTO。停止后应停止对应 DTO。

## 一段教学抓包的解释方法

下面的序列只展示分析方法，命令字节和 CAN ID 不是通用值：

```text
帧 1：Master -> ECU，CONNECT
      目的：建立会话
帧 2：ECU -> Master，RES
      目的：报告资源和最大长度
帧 3：Master -> ECU，SET_MTA
      目的：设置目标地址
帧 4：Master -> ECU，UPLOAD
      目的：请求若干字节
帧 5：ECU -> Master，RES + 原始数据
      目的：返回内存内容
帧 6...：DAQ 配置命令
帧 N...：ECU -> Master，DAQ DTO
      目的：按事件周期发送测量样本
```

分析时先标记阶段，再解释字段。不要看到一帧 8 字节数据就直接猜变量值。

## 如何验证 DAQ 周期

假设 Event Channel 配置为 10 ms：

1. 取连续 100 个相同 DAQ PID 的 DTO 时间戳。
2. 计算相邻帧间隔的平均值、最大值和最小值。
3. 对照控制任务周期和 CAN 仲裁延迟。
4. 检查是否存在丢帧、突发发送或停止后的残留帧。

平均间隔接近 10 ms 仍不代表采样点准确；还要确认 DTO 是在事件点采样后生成，而不是在发送任务稍后读取变量。

## 如何验证数值换算

```text
抓包原始字节 -> 按端序组成原始整数 -> 按 A2L 换算的物理值
```

建议用已知输入或边界值验证，并同时观察工具显示值、回读值和应用行为。

不要只保存截图，最好同时保存原始日志、A2L 版本、工具配置和测试条件。

## 现象到原因

| 现象 | 优先检查 |
| --- | --- |
| 无响应 | CAN 速率、XCP ID、ECU 是否启用、总线物理层 |
| CONNECT 成功但读变量失败 | A2L 地址、权限、内存段、地址扩展 |
| 单次读取正确，DAQ 错误 | ODT Entry、事件触发、DTO PID、端序 |
| 波形周期不对 | Event Channel 周期、任务抖动、发送队列 |
| 数值很大或负数异常 | 类型、符号位、端序、换算方法 |
| 停止 DAQ 后仍有数据 | Stop 流程、缓存排空、其他 DAQ List |

## 证据边界

抓包能证明总线上的命令、响应和周期，不能单独证明 ECU 内部变量计算正确，也不能证明 Flash 参数已经安全保存。需要把源码、A2L、抓包和台架现象关联起来。

## 推荐输出

一次完整分析至少包含：

1. 软件、A2L 和工具版本。
2. XCP CAN ID 和总线配置。
3. 命令响应时序。
4. 目标变量地址、类型和换算。
5. DAQ 的事件周期、ODT 布局和实际 DTO 周期。
6. 错误响应、丢帧和恢复行为。

## 抓包报告示例结构

```text
结论：连接成功，单次读取成功，DAQ 周期存在抖动。
证据：帧 1~5 完成连接和 UPLOAD；帧 6~20 完成 DAQ 配置；
      DTO 平均间隔 10.2 ms，最大间隔 18.6 ms。
可能原因：发送队列与其他高优先级 CAN 报文竞争。
待确认：控制任务实际触发时间、驱动发送队列水位、总线利用率。
```

报告要把抓包已证明的事实和需要源码或台架验证的假设分开。
