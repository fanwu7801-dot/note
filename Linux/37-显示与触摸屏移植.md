## 37.1 先分清显示链路和触摸链路

### 37.1.1 同一块屏上通常有两套独立设备

屏幕能显示画面和手指能控制界面，是两个独立问题。显示数据通过 MIPI-DSI 送到 LCD；触摸控制器通过 I2C 传递坐标，并通过中断通知处理器。

```text
显示：Android 图层 → SurfaceFlinger / Hardware Composer
                   → DRM / VOP2 的 VP → DSI Host / D-PHY → LCD

触摸：手指 → FT5306 → I2C + IRQ → Linux input
                              → Android InputReader / InputDispatcher → 应用
```

| 现象 | 已经说明什么 | 接着查什么 |
| --- | --- | --- |
| 背光亮、屏幕黑 | 背光电源及部分控制可能正常 | 图像通路、Panel 初始化、时序、复位 |
| 有完整画面、触摸无反应 | 显示通路基本可用 | I2C、触摸 IRQ、input 事件、Android 识别 |
| 触摸有事件、位置不对 | 触摸控制器已能上报 | 坐标范围、旋转、显示关联 |
| 开机 Logo 正常，进入 Android 黑屏 | 某阶段的显示已正常 | 内核接管、DRM 模式和 Android 合成服务 |

### 37.1.2 DRM 中几个经常出现的名称

DRM 是 Linux 显示框架。这里的 DRM 指 Direct Rendering Manager；不是多媒体版权保护中的 Digital Rights Management。

| 名称 | 初学时可以怎样理解 |
| --- | --- |
| Framebuffer | 描述一块可供显示的图像缓冲区，包括格式、尺寸、步长等；不等于一定存在 `/dev/fb0` |
| Plane | 从缓冲区取图像，可能进行裁剪、缩放和叠加 |
| CRTC | 控制一条扫描输出的时序和状态；Rockchip 上与具体 VOP/VP 能力对应 |
| Encoder / Bridge | 处理输出接口转换和连接 |
| Connector | 表示输出连接，例如 DSI、HDMI |
| Panel | 内置液晶面板，需要知道其时序、电源及初始化命令 |
| VP | RK3568 VOP2 的 Video Port，用于输出显示时序，不是屏幕编号 |

## 37.2 从屏规格书理解分辨率、时序与带宽

### 37.2.1 分辨率之外还要拿到哪些资料

移植前应拿到屏幕模组型号、接口针脚、电源电压、复位时序、MIPI lane 数、像素格式、Video/Command 模式、初始化序列及完整显示时序。只知道“800×1280 的 MIPI 屏”不足以完成移植。

`800×1280` 是有效显示区域；扫描还包含前肩、同步和后肩。屏幕通常不能像 HDMI 显示器那样，完全依靠 EDID 自动提供这些资料。

| 参数 | 实测值 | 含义 |
| --- | --- | --- |
| `hactive` / `vactive` | 800 / 1280 | 有效像素数 / 有效行数 |
| `hfront-porch` | 80 | 水平方向前肩 |
| `hsync-len` | 20 | 水平同步宽度 |
| `hback-porch` | 80 | 水平方向后肩 |
| `vfront-porch` | 20 | 垂直方向前肩 |
| `vsync-len` | 4 | 垂直同步宽度 |
| `vback-porch` | 12 | 垂直方向后肩 |
| `clock-frequency` | 60,000,000 Hz | 所请求的像素时钟；不是刷新率，也不是 MIPI lane 速率 |

### 37.2.2 用现有实测参数计算刷新率

对于这里的逐行扫描时序，名义刷新率可以按下式计算：

```text
Htotal = 800 + 80 + 20 + 80 = 980
Vtotal = 1280 + 20 + 4 + 12 = 1316

刷新率 ≈ PixelClock / (Htotal × Vtotal)
       ≈ 60,000,000 / (980 × 1316)
       ≈ 46.52 Hz
```

因此，这组配置不能仅因为 `clock-frequency = <60000000>` 就称为“60 Hz”。如果保持其他时序不变，60 Hz 对应的名义像素时钟为 `77,380,800 Hz`；这只是计算结果，**不是建议直接把实测配置改成这个值**。是否允许该时钟，应由屏规格、DSI 带宽、PLL 和实际运行模式决定。

驱动还可能对时钟进行取整或调整，应结合实际 DRM mode、时钟及画面表现确认。画面能稳定显示是实测事实；刷新率的标注需要另外核对。

### 37.2.3 像素时钟、DSI lane 和颜色格式

RGB888 每像素使用 24 bit，RGB565 每像素使用 16 bit。分辨率、刷新率或每像素位数增加，都会提高传输带宽要求；增加数据 lane 可以分担每条 lane 的负载。

以“60 MHz 像素时钟、RGB888、4 条数据 lane”为估算条件：

```text
每 lane 的数据率量级 ≈ 60,000,000 × 24 / 4
                   ≈ 360 Mbit/s/lane
```

该式用于建立数量级概念，未完整描述 DSI 包头、传输窗口和协议开销，不能直接当作最终 D-PHY 配置值。Video Burst、非 Burst 等模式的实际要求还要由 Host 驱动计算。

本篇实测片段没有列出全部 `dsi,lanes`、`dsi,format` 和 `dsi,flags`。它是基于原 SDK 包含文件的增量配置，缺省部分应沿 `#include` 和 Panel 驱动继续查找，不应误认为这些参数完全不需要。

### 37.3.3 沿包含关系找最终生效的节点

在 **Android SDK 的 kernel 目录**执行：

```bash
rg -n '#include|dsi1|route_dsi1|dsi1_in_vp0|vp0_out_dsi1' \
    arch/arm64/boot/dts/rockchip
rg -n 'simple-panel-dsi|panel-init-sequence|dsi,lanes|dsi,format|dsi,flags' \
    arch/arm64/boot/dts/rockchip drivers/gpu/drm/panel
```

重点看当前产品实际使用的顶层 DTS，而不是把搜索到的所有同名节点都修改。`panel@0` 如果已经在公共文件中存在，板级片段可能只覆盖部分属性；单独摘出这一段不一定是一份可独立编译的完整 DTS。

U-Boot Logo 与内核/Android 阶段也可能采用不同的设备树或资源。只更新某个阶段，可能产生“Logo 有、桌面无”或相反的现象。

## 37.4 读懂 panel-init-sequence

### 37.4.1 每条命令的格式

原厂 Panel 驱动将命令组织为：

```text
[Data Type] [发送后延时，ms] [Payload Length] [Payload ...]
  1 字节          1 字节           1 字节       指定长度
```

这些字节都按十六进制书写。三字节头是本 BSP 的设备树序列封装，不是让你手工填写整个线上 DSI 包的 ECC、CRC。

![原厂 Panel 命令格式说明](images/Android11适配补充/panel_command_format.png)

*图 37-2　原厂 Panel 指南 PDF 第 16 页的命令格式及示例；图中命令属于说明用样例，本板仍使用 37.3 的实测序列。*

### 37.4.2 从你的序列逐条解码

| 原记录 | 含义 |
| --- | --- |
| `29 00 03 E0 AB BA` | 类型 `0x29`，Generic Long Write；发送后等待 0 ms；有效负载 3 字节：`E0 AB BA` |
| `15 00 02 B0 00` | 类型 `0x15`，带一个参数的 DCS Short Write；负载为命令 `B0` 及参数 `00` |
| `05 C8 01 11` | 类型 `0x05`；负载为 DCS `0x11`，退出 Sleep；发送后等待 `0xC8 = 200` ms |
| `05 14 01 29` | 发送 DCS `0x29`，打开显示；发送后等待 `0x14 = 20` ms |
| `05 05 01 28` | 发送 DCS `0x28`，关闭显示；随后等待 5 ms |
| `05 78 01 10` | 发送 DCS `0x10`，进入 Sleep；随后等待 120 ms |

**第一个字节的 `0x29` 和负载中的 `0x29` 不是同一含义。** 前者是 DSI 包的数据类型，后者在相应 DCS 命令位置表示 Display On。

长序列中大量 `B1`、`C0` 等寄存器及参数属于屏控制 IC 的厂商初始化内容，应从屏供应商拿到匹配版本。屏接口和分辨率相同，也不能据此复用另一块屏的整张寄存器表。

### 37.4.3 修改序列时怎样避免低级错误

先逐条检查“声明的长度”和后面的实际字节数是否一致，再核对 Data Type、延时和命令顺序。不要把 C 数组中的逗号、`0x` 前缀或长度字段直接照搬成另一种驱动格式。

如果需要读 Panel 状态，应确认屏控制 IC 和当前 DSI Host 支持对应读取操作，由驱动或厂商调试接口执行；`i2cget` 不能读取 DSI Panel 的 DCS 寄存器。

## 37.5 电源、复位、背光与显示时序

### 37.5.1 按屏规格书建立上电顺序

常见过程是“电源稳定 → 复位及释放 → 发送初始化命令 → 退出休眠 → 打开显示 → 开背光”，具体顺序和等待时间服从屏规格书及驱动实现。

原厂 `simple-panel` 类驱动可能使用 `prepare-delay-ms`、`reset-delay-ms`、`init-delay-ms`、`enable-delay-ms` 等属性；各延时对应的实际位置要看本 SDK 驱动。重复在 GPIO 时序和命令序列中增加等待，虽然可能让屏亮起来，也会改变启动和休眠恢复时间。

### 37.5.2 背光亮度是另一套控制

LCD 背光常由 PWM、使能 GPIO 和电源共同控制。应检查背光节点的 `pwms`、极性、`brightness-levels`、默认亮度及其供电引用。

在 **板端 Android shell** 检查：

```sh
ls /sys/class/backlight
for item in /sys/class/backlight/*; do
    [ -d "$item" ] || continue
    echo "$item"
    cat "$item/max_brightness"
    cat "$item/brightness"
done
```

节点名需按实机确定。`brightness` 的范围由对应驱动定义，不必然是 0–255；Framework 的亮度数值也不等同于 PWM 原始占空比。

`vcc3v3_lcd1_n` 名称中的 `_n` 不能单独决定有效电平。本板代码使用了 `GPIO_ACTIVE_HIGH` 和 `enable-active-high`，应保留实测值，并按原理图及 regulator 驱动语义理解。

### 37.5.3 从故障发生阶段缩小范围

背光亮但没有图像，先确认 Panel 供电、复位和初始化，再看 VP→DSI 路由与时序。图像有规律地滚动、错行或花屏，更应检查时序、lane、像素格式及链路稳定性。

开机正常、熄屏后无法恢复，重点看 `prepare/enable/disable/unprepare` 路径、电源保持、复位和命令延时。不要只验证第一次点亮。

## 37.6 FT5306 触摸驱动与设备树

### 37.6.1 I2C、IRQ、RESET 各自做什么

FT5306 负责检测触点。I2C 用于访问控制器和读取触点数据，IRQ 提醒主机有事件，RESET 用于按要求复位控制器。

本板原笔记使用 FT5306，开启相应 ft5x06 驱动后，实测配置为：

```dts
&i2c1{
    status = "okay";
    ft5x061:ft5x06@38 {
        status = "okay";
        compatible = "edt,edt-ft5306";
        reg = <0x38>;
        touch-gpio = <&gpio3 RK_PA5 IRQ_TYPE_EDGE_RISING>;
        interrupt-parent = <&gpio3>;
        interrupts = <RK_PA5 IRQ_TYPE_LEVEL_LOW>;
        reset-gpio = <&gpio0 RK_PB6 GPIO_ACTIVE_LOW>;
        touchscreen-size-x = <800>;
        touchscreen-size-y = <1280>;
        touch_type = <1>;
    };
};
```

### 37.6.2 逐项理解实测属性

| 属性 | 本板取值与解释 |
| --- | --- |
| `&i2c1` | 触摸控制器所接 I2C 控制器；不是由 `@38` 决定 |
| `compatible` | `edt,edt-ft5306`；用它查找本 SDK 实际匹配的驱动 |
| `reg` | `0x38`，7 位 I2C 地址，不要再左移成 `0x70` |
| `interrupt-parent` / `interrupts` | GPIO3_A5，中断配置为低电平触发 |
| `reset-gpio` | GPIO0_B6；原笔记的单数属性名，不能擅自改成另一驱动的 `reset-gpios` |
| `touchscreen-size-x/y` | 800×1280；是否按标准 touchscreen 属性处理，要看实际驱动 |
| `touch-gpio` / `touch_type` | BSP 私有或特定驱动属性，检查源码中是否读取 |

主线可能使用 `edt-ft5x06` 一类驱动，BSP 也可能携带修改过的 ft5x06 驱动。不能只凭芯片名称推断实际启用的是哪一份：

```bash
rg -n 'edt,edt-ft5306|touch-gpio|touch_type|reset-gpio' \
    drivers/input/touchscreen
rg -n 'FT5|FTS|EDT' drivers/input/touchscreen/Kconfig \
    drivers/input/touchscreen/Makefile
```

再查看最终 `.config` 和启动日志。某个属性写进 DTS，但驱动没有读取，不会自动产生预想效果。

### 37.6.3 区分 GPIO 极性和 IRQ 触发方式

原实测 `touch-gpio` 的第三格写的是 `IRQ_TYPE_EDGE_RISING`，而 `interrupts` 中写的是 `IRQ_TYPE_LEVEL_LOW`。这里保留原记录，但这两个位置不能按同一语义解释。

GPIO specifier 的 flag 和 IRQ specifier 的 flag 属于不同约定，即使宏值碰巧相同，也不表示意义相同。尤其要检查该 BSP 是否仅用 `of_get_named_gpio()` 取得 GPIO 编号、是否实际解析 flag，以及中断究竟由哪段代码申请。

对于新的板卡或新的驱动，按它的绑定和源码填写 GPIO flag；本记录不作为把 IRQ 宏放入普通 GPIO 属性的通用模板。错误的中断极性或触发方式，可能导致没有事件或中断持续触发。

## 37.7 从 Linux input 走到 Android 触摸事件

### 37.7.1 先证明内核确实在上报触点

在 **主机终端**执行：

```sh
adb shell cat /proc/bus/input/devices
adb shell getevent -lp
adb shell dumpsys input
```

根据设备名称和能力找到触摸对应的 `eventX`。以下的 `eventX` 必须换成实际节点：

```sh
adb shell getevent -lt /dev/input/eventX
```

手指按下、移动、松开时，观察 `ABS_MT_POSITION_X/Y`、tracking ID、slot 和同步事件等。实际采用哪种多点触摸协议，由驱动决定。

没有 input 设备，先查驱动匹配和 probe；有设备但没有事件，查 IRQ、I2C 读数据与硬件；内核事件正常但 Android 无响应，再查 InputReader 分类、权限、显示关联和配置。

### 37.7.2 坐标范围和屏幕像素怎样关联

触摸芯片的原始坐标范围不一定恰好等于屏幕像素数。查看 `getevent -lp` 报告的 ABS 最小/最大值，再结合 `dumpsys input` 的校准和 viewport，理解 Android 怎样映射到显示区域。

交换 X/Y、翻转某一轴、把屏幕旋转 90°，是不同操作。标准 `touchscreen-swapped-x-y`、`touchscreen-inverted-x/y` 属性只有在当前驱动支持或调用相应通用 helper 时才会生效。不要同时在驱动、DTS 和 Framework 中重复旋转。

### 37.7.3 IDC 文件决定 Android 怎样理解触摸设备

IDC 不是 I2C 驱动，也不替代内核事件。它向 Android 描述设备的输入行为。

例如，下面只用于理解 IDC 的基础配置；本板已实测的配置以 37.7.5 为准，不需要为了本次唤醒额外添加 `device.internal`：

```ini
device.internal = 1
touch.deviceType = touchScreen
touch.orientationAware = 1
```

`touch.orientationAware` 表示考虑显示方向，不是任意指定“旋转 90°”的开关。文件名按 VID/PID 或 input 设备名匹配；设备名中的特殊字符可能转为下划线。通常检查本产品的 `/vendor/usr/idc/`、`/system/usr/idc/` 等实际打包目录，以 `dumpsys input` 显示的结果及该 Android 11 源码为准。[AOSP IDC 说明](https://source.android.com/docs/core/interaction/input/input-device-configuration-files)

### 37.7.4 熄屏后为什么触摸不一定能点亮屏幕

本板原有设备树和驱动配置完成后，亮屏时触摸可以操作界面，但熄屏后触摸不能点亮屏幕。**亮屏时有触摸事件**只能说明这一状态下的输入链路可用，并不自动意味着 Android 允许该设备在熄屏时发起唤醒。

从触摸到亮屏，可以分成几个环节：

```text
手指触摸
  → FT5306 产生触摸信息，驱动通过 IRQ 和 I2C 获取
  → Linux input 上报触摸事件
  → Android InputReader 读取设备的 IDC 和触摸事件
  → Android 输入和电源策略判断是否唤醒
  → 显示恢复，屏幕点亮
```

IDC（Input Device Configuration）是 Android 输入设备配置文件。对于内置触摸屏，Android 的默认策略可能不把普通触摸作为唤醒事件，以减少误触唤醒；具体默认值和实现要以产品源码及设备识别结果为准。本板在 IDC 中设置 `touch.wake = 1` 后，触摸事件可以按唤醒事件参与 Android 的策略处理。**用户已在本板 Android 11 原厂 SDK 上实测该方法可用。**

如果想结合源码观察这项配置，在 **Android SDK 根目录**执行：

```bash
grep -R -n -E 'touch\.wake|POLICY_FLAG_WAKE' frameworks/native/services/inputflinger
```

`grep -R` 递归查找，`-n` 显示行号，`-E` 启用扩展正则；`touch\.wake` 中的反斜杠表示匹配名称里的点，`|` 表示查找两个词之一。先找到读取 `touch.wake` 的代码，再查看触摸按下时如何为事件设置唤醒策略标志。AOSP 的相关实现会为允许唤醒的触摸事件附加 `POLICY_FLAG_WAKE`，后续由系统策略处理；本板源码路径和细节以该 SDK 的搜索结果为准。

这项配置属于 Android 输入策略：它不负责给触摸芯片供电，也不会单独把普通 GPIO 改造成硬件唤醒中断。如果系统已经进入需要硬件唤醒源的深度休眠，触摸芯片、中断、驱动电源管理和内核唤醒配置还必须支持对应状态。亮屏、仅屏幕关闭与系统深度休眠要分别测试，不能把一种状态的成功直接推广到另一种状态。

### 37.7.5 创建本板的 IDC 并加入产品配置

本节使用**迅为 RK3568 Android 11 原厂 SDK**，不是前面 Linux 6.1 驱动 SDK 或独立最小系统。涉及 SDK 源码和构建的操作在 Android SDK 根目录执行；ADB 命令在连接开发板的主机终端执行。先确认实际触摸设备名称：

```sh
adb shell getevent -lp
```

`adb shell` 在开发板 Android 中执行命令；`getevent -lp` 列出 input 设备名称及其事件能力。本板实测名称为 `generic ft5x06 (79)`；其他芯片、驱动或版本可能不同，必须按实际名称匹配。

**第一步：创建 IDC。** 在 SDK 中新建 `device/rockchip/rk356x/rk3568_r/generic_ft5x06__79_.idc`，内容为：

```ini
touch.deviceType = touchScreen
touch.orientationAware = 1
touch.wake = 1
```

三个属性的作用分别是：

| 属性 | 作用 |
| --- | --- |
| `touch.deviceType = touchScreen` | 将设备按与显示屏关联的触摸屏处理。 |
| `touch.orientationAware = 1` | 让触摸坐标处理考虑关联显示屏的方向；它本身不是唤醒开关，也不是固定旋转 90°。 |
| `touch.wake = 1` | 允许触摸事件作为 Android 唤醒策略的输入；这是本次改善熄屏触摸唤醒的关键配置。 |

该文件名中的 **两个连续下划线是正确的**。本 SDK 的设备名匹配会将空格和括号等不适合作为文件名的字符分别替换为下划线：

```text
input 设备名：generic ft5x06 (79)
IDC 文件名：  generic_ft5x06__79_.idc
```

`ft5x06` 后面一个下划线来自空格，另一个来自左括号；末尾的下划线来自右括号。文件名中的数字、大小写和下划线都要与实际匹配结果一致。芯片型号为 FT5306，并不意味着 IDC 文件名就应写成 `FT5306.idc`；这里依据的是驱动上报的 **input 设备名称**。

**第二步：将文件加入产品构建。** 打开产品配置文件 `device/rockchip/rk356x/rk3568_r/rk3568_r.mk`，增加以下内容；如果已经存在同一目标路径的复制规则，先检查并避免重复添加：

```makefile
PRODUCT_COPY_FILES += \
    device/rockchip/rk356x/rk3568_r/generic_ft5x06__79_.idc:$(TARGET_COPY_OUT_VENDOR)/usr/idc/generic_ft5x06__79_.idc
```

`PRODUCT_COPY_FILES` 是 Android 产品构建使用的文件复制列表；`+=` 表示追加一项，反斜杠表示这一条 Make 语句继续到下一行。冒号左侧是相对于 SDK 根目录的源文件，右侧是构建产物中的目标路径；`$(TARGET_COPY_OUT_VENDOR)` 指向该产品的 vendor 输出目录。因此镜像部署后，设备上的目标文件为 `/vendor/usr/idc/generic_ft5x06__79_.idc`。只在源码树创建文件而没有加入产品构建，文件不会因此自动进入镜像。

本板 SDK 的这套查找路径按 `/odm/usr/idc`、`/vendor/usr/idc`、`/system/usr/idc` 的顺序查找相应配置；放在 vendor 路径即可。Android 也可能按设备标识尝试其他候选文件名，且其他 Android 版本或厂商修改可能不同。如果存在多个候选配置，不要仅凭文件存在推断最终加载了哪一份，应结合 `dumpsys input` 和本 SDK 源码确认。

**第三步：编译和部署。** 使用第 36 篇已经选好的 `rk3568_r` 产品配置及本板现有的构建、更新镜像流程，更新包含该 vendor 文件的镜像，然后重启开发板。本次更改位于 Android 产品配置，不能只重新编译内核或 DTB 就认为 IDC 已经部署到设备。

### 37.7.6 验证文件、匹配结果和触摸唤醒

以下命令在连接开发板的**主机终端**执行；`adb devices` 应显示目标设备。多台设备同时连接时，先按第 36 篇选择目标设备。

```sh
adb devices
adb shell cat /vendor/usr/idc/generic_ft5x06__79_.idc
adb shell getevent -lp
adb shell dumpsys input > android-input-wake.txt
```

第一条列出 ADB 设备；第二条读取设备上实际部署的 IDC 内容；第三条重新确认设备名；第四条把 Android 输入系统状态保存到主机当前目录的文本文件。`>` 会覆盖同名文件。打开 `android-input-wake.txt`，查找 `generic ft5x06 (79)`、配置文件路径及设备参数；不同 BSP 的输出字段可能有差异。如果显示了配置文件路径和 Wake 状态，检查它们是否对应本文件及启用状态。**文件存在只是部署成功的证据，实际被匹配和读取还需结合输入系统状态确认。**

然后按本板原有操作使屏幕熄灭，再触摸屏幕，观察是否点亮；点亮后再验证坐标、旋转和正常操作。重复测试冷启动后的多次熄屏及唤醒，并记录测试使用的是哪种休眠状态。唤醒用的第一次触摸是否同时传给应用取决于系统策略，应以实际行为为准。

### 37.7.7 如果仍不能唤醒

| 现象 | 下一步检查 |
| --- | --- |
| 设备上没有 IDC | 产品是否为 `rk3568_r`，复制规则是否生效，更新的是否包含 vendor 内容，设备是否已经重启。 |
| 文件存在但未被匹配 | `getevent -lp` 的实际设备名、两个下划线、其他候选 IDC 和搜索优先级；检查 `dumpsys input`。 |
| 唤醒正常但方向或位置不对 | 单独检查坐标范围、方向和显示关联；不要把 `touch.orientationAware` 当作直接设置固定角度。 |
| 亮屏有触摸，熄屏后无事件 | 排查触摸控制器供电、驱动休眠、IRQ 和实际休眠状态；仅修改 IDC 无法保证事件产生。 |
| 屏幕关闭可唤醒，深度休眠不行 | 进一步核对触摸芯片的低功耗模式、IRQ 硬件唤醒及驱动/内核电源管理，不能直接认定 IDC 无效。 |

例如，可在确认设备节点后通过 `adb shell getevent -lt /dev/input/eventX` 观察事件，`eventX` 必须换成实际编号。ADB 或持续监控本身可能影响系统进入休眠，因此观察到的结果要结合实际休眠状态判断；不同版本的日志及权限要求也可能不同。

## 37.8 Android 11 上的验证与排错

### 37.8.1 先检查驱动，再检查 Android 显示服务

```sh
adb shell dmesg
adb shell ls /sys/class/drm
adb shell dumpsys display
adb shell dumpsys SurfaceFlinger
adb shell dumpsys input
adb logcat -b all -d > android-display-input.log
```

`dmesg` 等命令可能需要第 36 篇的 userdebug/root 环境。若内核提供且已挂载 debugfs，可进一步读取 `/sys/kernel/debug/dri/0/summary` 或 `state`；这些节点因 BSP 而异，先 `ls` 再用，不把某个调试文件存在视为所有版本的保证。

`modetest` 只有实际安装后才可用。Android 图形服务已占用 DRM 时，额外进行 modeset 可能争用资源；先以读取状态和日志为主。

### 37.8.2 现象到检查位置

| 现象 | 优先检查 |
| --- | --- |
| Panel 或 DRM 延迟 probe（如 -517） | regulator、背光、GPIO、PHY 或 Panel 等依赖是否就绪 |
| DSI 发送命令超时 | 电源、复位、PHY、lane、LP/HS 和初始化命令类型 |
| 有 Logo、无 Android 画面 | 内核镜像是否更新，DRM 状态，HWC/SurfaceFlinger 日志 |
| 颜色异常或有规律错位 | RGB 格式、时序、像素时钟、实际 lane 和传输模式 |
| 触摸无事件 | 驱动匹配、I2C 地址、IRQ 计数、复位 |
| 触摸有事件但 Android 不接收 | input 能力、IDC、设备权限和 InputReader 状态 |
| 触摸坐标反向或旋转错误 | 原始范围、轴变换、display viewport 与方向配置 |
| 熄屏后触摸不能点亮 | 先按 37.7.5 核对 IDC 和 `touch.wake`，再按实际休眠状态检查事件、IRQ 与供电 |
| 已唤醒但画面未恢复 | Panel 供电、退出/恢复序列、背光及显示状态 |

### 37.8.3 完成适配的验收记录

记录屏幕/触摸 IC 型号、DTS 文件及其版本、分辨率、实测刷新率、像素时钟、lane/格式、初始化序列来源、input 名称、IDC 文件和镜像哈希。

至少覆盖冷上电、Android 进入桌面、亮度调节、全屏颜色图、四角与中心触摸、多点操作、旋转及熄屏恢复。保存“能亮”的配置以后，再单独改善刷新率、启动耗时或休眠体验。
