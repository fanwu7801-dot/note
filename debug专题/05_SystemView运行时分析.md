# 05_SystemView 运行时分析：从任务调度到问题定位

整理日期：2026-10-22。

SystemView 是 SEGGER 的嵌入式运行行为分析工具。它把目标程序记录的
任务切换、中断和用户事件放在同一条时间轴上，帮助我们回答：
**什么时候发生了什么，谁占用了 CPU，后面的工作为什么没有及时执行。**

本文以单核 Cortex-M 和 FreeRTOS 为主要教学背景。
所有时间、频率和任务安排都是明确条件下的例子，没有对实际板卡进行
移植、编译、烧录或抓取，不代表某个车辆项目的实测结果。

## 1. 为什么有断点和 printf，还需要 SystemView

假设控制任务每 10 ms 处理一次数据，车辆偶尔出现一次响应延迟。

用断点可以检查变量、调用栈和分支，但停住 CPU 会改变后续调度。
用日志可以看到“已经执行到这里”，但两条日志之间可能包含任务抢占、
中断、锁等待和队列等待，单凭两行文字难以分清。

SystemView 为这些事件建立有时间关系的记录。分析的重点从“某个变量
现在是什么”扩展到“多个执行上下文在这段时间怎样交互”。

| 工具 | 擅长回答的问题 | 需要注意的边界 |
| --- | --- | --- |
| 断点、单步 | 分支为何成立，变量和寄存器是什么 | 停机会改变运行时序 |
| 栈回溯 | 故障现场经过了哪些函数调用 | 通常不保留完整调度历史 |
| printf、RTT 文本日志 | 业务代码主动报告了什么 | 格式化和传输也有开销 |
| SystemView | 谁在运行，何时被唤醒，哪里发生等待 | 依赖已接入的事件记录 |
| 示波器、逻辑分析仪 | 引脚何时翻转，电平和总线是什么 | 需与软件事件建立对应 |

例如，SystemView 记录“请求打开输出”的时刻；示波器测量实际输出电压。
两者结合，才能区分软件发出请求的延迟与驱动、电源和执行器的响应延迟。

## 2. 先理解 RTOS 中的三个对象

### 2.1 任务：调度器选择的执行主体

一个任务拥有自己的入口、栈、优先级和运行状态。
在单核 MCU 上，一个时刻只能执行一个 CPU 上下文；多个任务通过切换
交替运行，硬件中断又可能打断当前任务。

常见任务状态如下：

| 状态 | 含义 | 例子 |
| --- | --- | --- |
| Running，运行 | 当前得到 CPU | 正在解析一帧 UART 数据 |
| Ready，就绪 | 具备运行条件，正在等待调度 | 通知已到，但更高优先级任务在运行 |
| Blocked，阻塞 | 等待事件、资源或时间条件 | 等待接收队列或延时到期 |
| Suspended，挂起 | 被显式挂起 | 通过挂起接口暂停某项工作 |

**任务被唤醒，通常只表示从阻塞变为就绪，不代表已经开始运行。**

这句话是阅读 SystemView 时间线的基础。
任务就绪后，可能还要等中断返回、更高优先级任务结束或调度恢复。
任务优先级数值方向与 NVIC 中断优先级编码方向也不能混为一谈。

### 2.2 中断：硬件事件的执行上下文

UART 接收、DMA 完成、定时器和 CAN 接收等事件都可能触发 ISR。
ISR 中可以做快速确认、收集信息和请求唤醒任务，较长处理通常交给任务。

中断能否抢占其他中断，取决于 MCU、优先级分组、屏蔽状态和具体配置。
FreeRTOS 的任务优先级不会直接替代 NVIC 的中断优先级。

### 2.3 调度器：决定接下来运行哪个任务

在常见抢占式配置下，更高优先级任务就绪后会引发相应调度。
具体切换点还受移植层、中断退出路径和临界区等条件影响。

分析时要区分：通知是否发出、任务是否进入 Ready、是否提出切换请求、
任务何时真正运行。这几个时刻可能不同。

## 3. SystemView 的完整工作链路

典型的 RTT 方案包含以下过程：

1. RTOS 适配接口、ISR 记录点或业务记录点发现事件。
2. SystemView 目标端代码读取时间戳，编码事件类型和必要参数。
3. 事件数据进入目标 RAM 中的 RTT 通道缓冲区。
4. 调试探针读取目标 RAM，将记录传到电脑。
5. SystemView 主机软件解析事件，显示时间线和统计信息。

因此，它需要目标端配合。只安装电脑软件，不能自动知道任意固件里的
全部任务状态、互斥锁归属或函数调用。

### 3.1 它记录事件，不等于记录每条指令

任务切换事件可能说明 TaskA 从某一时刻开始执行，但不会天然列出
TaskA 运行期间的每一条机器指令。

如果要知道协议解析函数什么时候开始、什么时候结束，需要接入对应
记录点，或者使用适用的其他跟踪机制。未记录的业务动作不能凭空还原。

例如，时间线上看到 TaskA 连续执行 2 ms，还需要进一步划分业务阶段，
才能知道时间花在数据校验、CRC、内存复制还是轮询外设。

### 3.2 谁负责记录哪些事件

| 记录来源 | 典型事件 | 是否天然覆盖全部情况 |
| --- | --- | --- |
| RTOS 适配层 | 任务切换、就绪、阻塞、部分内核 API | 取决于版本和适配覆盖 |
| ISR 入口、出口接入 | 中断执行区间与嵌套关系 | 需要实际接入相应中断 |
| 用户记录点 | 业务阶段、错误、关联序号 | 由开发者定义 |
| 部分模块专用适配 | 软件定时器、资源等事件 | 取决于目标模块和配置 |

没有看到某个中断，可能是它未发生，也可能是没有接入记录。
没有看到任务阻塞原因，也可能是对应 API 事件没有被记录。

## 4. SystemView、RTT、J-Link、SWD 和 SWO 的关系

| 名称 | 本文中的职责 |
| --- | --- |
| SystemView 目标端代码 | 生成带时间信息的事件记录 |
| RTT | 在目标 RAM 中组织双向数据通道 |
| J-Link | 通过调试连接访问目标，并向电脑提供数据 |
| SWD / JTAG | 调试探针与芯片之间的调试访问接口 |
| SWO | 部分芯片支持的另一类跟踪输出通道 |
| SystemView 主机软件 | 解析、显示和分析事件 |

常见的 SystemView + RTT + J-Link 方案，通过已有调试连接读 RAM，
不额外占用 UART 引脚，通常也不要求 SWO 引脚。
这不表示调试接口可以不接，也不表示每颗芯片、每个探针都支持连续读取。

### 4.1 RTT 的核心是 RAM 中的缓冲区

目标端维护 RTT 控制块和各通道缓冲区。
控制块包含通道描述、缓冲区地址、大小以及读写位置等信息；
主机据此知道哪里有新数据。

Up 通道表示目标到主机，Down 通道表示主机到目标。
普通文本常使用 Up 0；SystemView 常见配置使用通道 1。
具体通道、数量和命令通道安排必须核对所用版本的目标配置。

不要把普通文本写入正在承载 SystemView 二进制事件的通道。
多个主机工具也不要未经确认就同时消费同一个 RTT 通道，
否则记录可能被另一个读者取走。

### 4.2 RTT 也有阻塞和非阻塞行为

一般 RTT 通道可以配置不同的满缓冲区处理方式：

- 阻塞写：等待空间，可能拖延调用它的任务或 ISR。
- 非阻塞跳过：空间不足时放弃本次写入。
- 非阻塞截断：一般数据写入接口可能只写能容纳的部分。

SystemView 事件是有格式的数据包，应使用配套记录库和缓冲策略，
不能把任意截断字节当成完整事件，也不能随意改变库的写入方式。
分析实时问题时，应核实无主机读取、缓冲区满时目标端的实际行为。

## 5. 时间戳为什么不一定来自 SysTick

FreeRTOS 的 Tick 主要服务于内核计时和调度。
假设 Tick 周期为 1 ms，用它区分几十微秒的 ISR 耗时通常不够。

SystemView 需要适合目标平台的时间戳源，可能使用可用的周期计数器或
硬件定时器。部分 Cortex-M 可以使用 DWT 的周期计数能力，但不能认为
所有 Cortex-M 都具备相同单元、权限和低功耗行为。

时间换算的基本关系是：

```text
经过时间 = 时间戳计数差 / 时间戳计数频率
```

教学例子：计数器频率为 100 MHz，两条事件相差 5,000 个计数，
对应 50 μs。这里的 100 MHz 是时间戳源频率，不一定等于内核 Tick 频率。

### 5.1 四个必须核对的问题

1. 时间戳计数器是否已经启动，读取是否可靠？
2. 记录库配置的时间戳频率是否与实际频率一致？
3. 时钟切换、休眠和调试暂停时，计数器是否继续运行？
4. 计数器有效位宽、回绕与记录库处理方式是否匹配？

32 位计数器按 100 MHz 递增时，约 42.95 s 回绕一次。
这不等于只能录制 42.95 s，而是要求计数差、位宽配置和回绕处理符合
所用记录库的要求，长时间无事件和低功耗也需要验证。

时间显示很精细，只能说明显示分辨率。
实际测量精度还受时间戳源、记录点位置、读取开销和接入方式影响。

## 6. 时间线上最重要的五个时间量

| 时间量 | 本文定义 | 用途 |
| --- | --- | --- |
| 计划释放时刻 | 按周期或设计要求应触发工作的时刻 | 检查周期是否偏离 |
| 实际就绪时刻 | 任务实际进入 Ready 的时刻 | 检查唤醒和调度边界 |
| 首次开始时刻 | 本次工作第一次得到 CPU 的时刻 | 计算启动等待 |
| 完成时刻 | 本次业务处理完成的时刻 | 检查响应时间和截止时间 |
| CPU 执行时间 | 本次工作实际占用 CPU 的各段时间之和 | 分析处理成本 |

“任务切换出去”也不等于“本次业务完成”，可能只是被抢占或暂时阻塞。
需要业务完成事件才能确定一轮工作在哪里结束。

### 6.1 启动等待、墙钟耗时与 CPU 时间

```text
就绪后的启动等待 = 首次开始时刻 - 实际就绪时刻
开始到完成的墙钟耗时 = 完成时刻 - 首次开始时刻
释放到完成的响应时间 = 完成时刻 - 实际释放时刻
CPU 执行时间 = 本次工作各段实际执行区间之和
```

本文把周期性工作的计划起点与实际释放时刻分开记录。
分析相对计划的整体延迟时，还要从计划时刻开始计算，不能只看 Ready。
如果唤醒它的 Tick 中断本身被推迟，Ready 事件就可能已经晚了。

函数开始、结束两个用户事件的时间差，通常得到墙钟耗时；
期间的中断、抢占和阻塞都可能包含在内。
要计算 CPU 时间，需要结合完整的上下文切换和 ISR 事件。

### 6.2 周期抖动与截止时间

假设计划开始时刻为 0、10、20、30 ms，实际开始为
0.1、10.3、20.2、30.7 ms。
对应的启动偏差是 0.1、0.3、0.2、0.7 ms。

这与“相邻实际开始的间隔”是两个统计口径。
做报告时必须写清楚抖动的定义和参考点。

如果要求每轮工作在计划时刻后 2 ms 内完成，就应检查每轮的完成时刻
是否越过这个边界。平均负载低不保证每轮满足截止时间。

## 7. 一个完整例子：CAN 到达后，控制任务为什么晚了

以下数据完全是教学假设，单位为 ms。
假设接收事件在 10.00 到达，对应任务在 10.05 进入 Ready。

| 区间或时刻 | 事件 | 对控制任务的影响 |
| --- | --- | --- |
| 10.00～10.05 | CAN ISR 接收并发出通知 | 形成待处理工作 |
| 10.05 | 控制任务进入 Ready | 可以参与调度 |
| 10.05～10.20 | CAN ISR 完成剩余工作 | 控制任务暂未运行 |
| 10.20～10.80 | 更高优先级任务运行 | 控制任务继续等待 |
| 10.80～11.00 | 控制任务运行 | 执行 0.20 ms |
| 11.00～11.30 | 另一个 ISR 抢占 | 本次控制工作暂停 |
| 11.30～11.60 | 控制任务继续并完成 | 再执行 0.30 ms |

由这些假设可以算出：

- 就绪后的启动等待：10.80 - 10.05 = **0.75 ms**。
- 开始到完成的墙钟耗时：11.60 - 10.80 = **0.80 ms**。
- 控制任务自身 CPU 执行时间：0.20 + 0.30 = **0.50 ms**。
- 从接收事件到完成：11.60 - 10.00 = **1.60 ms**。

如果需求是接收事件后 1 ms 内完成，这轮就已经超期，
即使控制任务自身只需要 0.50 ms。

改进也要对准原因：减少接收 ISR 的尾部工作、评估高优先级任务预算、
缩短抢占 ISR 或调整业务安排。只优化控制算法本身不一定足够。
任何优先级变更都要重新检查其他任务的响应时间。

## 8. 怎样阅读 SystemView 的几个主要视图

不同版本的界面名称和布局可能不同，下面讲分析职责。

### 8.1 Timeline：先看谁占用了时间

先定位发生故障的时间窗口，再依次看：

1. 目标任务是否已经就绪？
2. 没运行的区间里，CPU 正在执行哪个任务或 ISR？
3. 运行后是否被多次抢占？
4. 切换出去是等待资源，还是被更高优先级上下文抢占？

不要只凭某种颜色做判断；结合当前版本图例、事件列表和上下文信息。

### 8.2 Events：把时间关系落实到具体事件

事件列表用于检查通知、内核调用和任务切换的先后顺序。
例如“ISR 发出通知 → 任务 Ready → ISR 退出 → 任务开始运行”。

只有相邻关系不足以证明业务因果。并发消息要有序号或关联标识，
才能确认哪个接收事件对应哪次解析和输出。

### 8.3 Contexts 和统计：比较占用与次数

任务、中断的运行次数、累计时间和单次时间统计可以帮助寻找热点。
但任务一次连续运行片段，未必等于一次完整业务处理。

一个任务可能在一轮业务里运行、阻塞、再运行多次。
用上下文统计推导业务处理时间前，要先明确统计单位。

### 8.4 日志与用户事件：给时间线增加业务含义

“任务运行了”很宽泛；“开始校验第 128 帧”“发布第 128 帧结果”
能够把调度行为和业务链对应起来。

不同功能需要相应版本和目标端接入支持，不能因为主机界面存在某个
窗口，就认为当前固件已经提供了全部数据。

## 9. CPU 利用率为什么不能直接证明实时性

在单核、观察完整、Idle 归类准确的条件下，可以用观察窗口内的
非 Idle 时间占比粗略描述 CPU 忙碌程度。

但具体软件的任务、ISR、调度器占用如何归类，应核对统计口径。
不能把已经包含中断的某种累计时间再重复加一次。

以下两种情况都可能发生：

- 平均 CPU 只忙 20%，但某次长 ISR 仍然让控制任务错过截止时间。
- CPU 忙 80%，但经过正确的预算和调度，关键任务仍然按时完成。

还要检查观察窗口长度、峰值负载、事件是否丢失、休眠是否影响时间源。
报告中应同时列出负载和关键链路延迟，而不是只展示一个百分比。

**一段记录里的最大值，是已观察最大值，不能直接等同于已证明的 WCET。**
最坏执行时间还取决于路径覆盖、输入组合、缓存和其他平台条件。

## 10. 接入 FreeRTOS 前，应确认哪些工程条件

SystemView 的移植与 FreeRTOS 版本、内核跟踪接口和现有工具有关。
应选与实际版本匹配的官方适配资料，不把某个旧教程的补丁套到全部版本。

| 检查项 | 要回答的问题 |
| --- | --- |
| 平台 | 芯片、内核、调试探针是否支持计划采用的传输方式？ |
| RTOS | 实际 FreeRTOS 版本、port 和跟踪接口是什么？ |
| 现有跟踪 | 是否已有其他 recorder 或 trace 宏占用？ |
| 时间源 | 来源、频率、位宽、回绕、低功耗行为是否明确？ |
| 内存 | 控制块和缓冲区在哪里，探针能否访问？ |
| 并发 | 任务与嵌套中断写事件时，库的锁保护是否正确？ |
| 资源 | Flash、RAM、各任务栈和中断栈能否容纳额外开销？ |
| 启动 | 记录库何时初始化，是否覆盖所需的启动事件？ |

官方提供多种 RTOS 和版本的接入方式。
本文不规定所有版本都应采用同一组宏，也不要求手改生成文件或内核源码。

### 10.1 推荐的实施顺序

1. 记录芯片、RTOS、编译器、库版本和当前 Git 提交。
2. 确认时间源和 RTT 通道，选择匹配的官方目标端源码与适配。
3. 在工程允许的手写配置或适配位置接入，检查已有 trace 宏冲突。
4. 在合适的初始化阶段完成配置，并核对任务信息是否可以被报告。
5. 接入需要观察的 ISR，再逐步增加业务记录点。
6. 编译并检查 RAM、Flash、栈以及配置完整性。
7. 先用已知周期任务与硬件参考信号校验时间轴，再分析复杂故障。

如果工具生成的配置需要改变，应修改生成源或正式用户扩展位置。
不能为了接入记录而直接修改下一次生成就会覆盖的文件。

### 10.2 为什么要先校验时间轴

假设任务使用已知时间基准周期唤醒，应先比较多个周期的记录间隔。
必要时让 GPIO 在同一业务边界翻转，并用示波器或逻辑分析仪交叉测量。

GPIO 翻转和记录事件不可能毫无间隔，应明确先后顺序及其固定开销。
测量出现成比例的偏差时，优先排查时间戳频率和时钟配置。

## 11. UART + DMA 项目怎样布置业务事件

结合本仓库的串口学习内容，可以把接收链分成以下阶段：

1. DMA 或串口中断确认新数据边界。
2. 接收模块发布可用块并通知解析任务。
3. 解析任务取得数据，逐步执行帧解析状态机。
4. 校验通过后发布有效帧。
5. 业务任务处理有效帧并发布结果。

建议记录能够回答具体问题的事件，而不是无目的地逐字节打印。

| 事件语义 | 建议附带的信息 | 能回答的问题 |
| --- | --- | --- |
| 接收块形成 | 块序号、长度 | 数据何时可用？ |
| 通知或入队结果 | 成功或失败、关联序号 | 是否丢在交接处？ |
| 解析开始 | 同一关联序号 | 等了多久才解析？ |
| 帧校验结果 | 帧序号、结果码 | 时间花在何处，失败原因是什么？ |
| 业务发布 | 同一帧序号 | 从接收到处理完成用了多久？ |

接收块可能跨多帧，一帧也可能跨多个块。
块序号与帧序号之间要建立实际映射，不能直接认为一块就等于一帧。

记录时间线也不会自动修复 DMA 缓冲区所有权。
如果解析任务收到的是指针，还应检查解析时数据是否已经被 DMA 覆盖。
这些生命周期约束可结合序号、缓冲区编号和丢弃计数进行验证。

## 12. 用户事件怎样设计才有用

先从问题出发，再决定记录点。
如果问题是“控制延迟”，优先覆盖输入、交接、开始、完成和异常结果。

记录中应尽量包含：

- 稳定的事件含义，例如“校验完成”，避免同一 ID 在各处表示不同动作。
- 可关联的序号，用于区分同时在途的帧或请求。
- 有限且必要的参数，例如长度、结果码和队列积压量。
- 成功、超时、丢弃和恢复路径，避免只记录成功。

开始、结束标记要考虑嵌套和并发。
同一 ID 的区间如果可以被多个任务同时使用，需要按上下文或关联标识
区分；发生提前返回时也要保证记录语义完整。

不要在高频 ISR 中进行大量字符串格式化、遍历整个缓冲区或输出整帧。
用户事件的具体 API 和可传参数数量，应查所用版本头文件和手册。

## 13. 缓冲区为什么会溢出

事件产生速度长期高于主机读取速度，有限缓冲区最终就会填满。
即使平均速度足够，某段突发或主机暂停读取仍可能造成溢出。

教学估算：假设平均每个事件编码后占 12 B，每秒产生 10,000 个事件，
平均写入约为 120,000 B/s；主机停读 20 ms，就会新增约 2,400 B。

这只是容量估算，实际事件长度可变，还要计入命令、元数据、
同时发生的突发和实际可用空间。

可采取的办法包括：

- 减少不必要的高频事件，保留故障链路需要的信息。
- 在 RAM 预算内增加缓冲区，为短时停读提供余量。
- 检查调试访问速度、探针能力和其他调试窗口的读取负担。
- 对只需短时间观察的问题，选择适用的记录模式或缩小范围。

缓冲区变大只能缓解短时积压，不能解决长期生产速度高于消费速度。
出现 overflow 或数据丢失后，受影响区间的时序与统计应重新评估，
不能继续当成完整记录来证明“没有发生异常”。

## 14. 三种记录方式应该怎样选择

| 方式 | 适用问题 | 主要限制 |
| --- | --- | --- |
| 连续记录 | 长时间观察任务、中断和偶发延迟 | 需要持续可用的传输带宽 |
| 单次记录 | 在有限窗口内观察启动或某次操作 | 受目标端缓冲容量限制 |
| 事后分析 | 保留故障前的近期历史，故障后取出 | 需正确配置覆盖与停止机制 |

这些模式需要按记录库和工具支持方式配置。
默认 RTT 通道在满时跳过新数据，不代表它已经自动具备“持续保留最后
几秒历史”的事后记录能力。

如果故障后立即复位或掉电，RAM 中的数据可能丢失。
故障停止、看门狗、重启和数据保留必须作为整体方案设计。

## 15. 典型问题应如何沿证据链排查

| 现象 | 先看什么 | 再核对什么 |
| --- | --- | --- |
| 任务周期偶尔延后 | 计划、Ready、开始三个时刻 | 长 ISR、调度挂起、优先级负载 |
| 任务一直没运行 | 是否就绪，还是仍在阻塞 | 等待对象、超时、通知语义 |
| 高优先级任务很慢 | 是否在等低优先级持锁者 | 锁拥有者、持锁时间、继承情况 |
| 大量切换但吞吐低 | 单次有效工作与唤醒频率 | 通知粒度、无效唤醒、短周期轮询 |
| 软件定时器回调延后 | 定时器服务任务正在执行什么 | 前一个回调、服务任务阻塞 |
| UART 解析积压 | 接收块到解析开始的延迟 | 队列峰值、满计数、缓冲生命周期 |
| ISR 占用突然增加 | 进入频率与单次时长 | 中断源、清标志、真实外设行为 |
| 输出晚于业务完成 | 业务完成到驱动输出的边界 | 下游队列、总线周期与实际电压 |

“时间接近”首先是定位线索。
要宣布原因，应结合关联序号、源码路径、配置和针对性复现验证。

## 16. 为什么记录本身也可能改变程序

每次记录都要执行代码、读取计数器并写缓冲区，因此会使用 CPU、RAM、
Flash 和栈。并发保护也可能改变极短时间窗口。

调试连接还可能影响休眠条件或 RAM 后台访问。
带缓存的平台需要确认缓冲区可见性、对齐和缓存一致性要求；
不能把另一颗无缓存 MCU 的经验直接套用。

建议比较关闭记录、启用最少记录、启用完整记录三个构建或配置的表现，
保留相同负载条件。若只有完整记录时才出现延迟，要先评估观测开销。

官方介绍中的典型开销依赖测试平台和事件频率。
不能把它当成当前芯片的固定 CPU 占用或精确内存预算。

## 17. 用 cfg / ctx / data / ops 检查接入边界

四元组用于检查职责，不要求把第三方库重构成统一大结构体。

| 分类 | 在记录方案中的映射 | 边界 |
| --- | --- | --- |
| cfg | 时间源频率、缓冲容量、通道、事件开关 | 来自受控配置，不随业务任意改写 |
| ctx | 记录状态、读写索引、内部同步状态 | 由记录库或所属模块维护 |
| data | 已记录事件、关联序号、丢失计数与分析结果 | 带清楚的时间与完整性说明 |
| ops | 初始化、开始、停止、提交业务事件 | 通过正式接口请求行为 |

业务模块可以发布“收到请求”“处理完成”等事件。
它不应直接改 RTT 的读写索引，也不应为了记录而修改另一个模块的
状态机内部变量。

记录服务应观察业务，不应成为关键控制功能必须等待的远程消费者。
无主机连接或记录资源不足时，业务如何继续运行需要明确验证。

## 18. 一个可以照着做的学习实验

前提：有一个允许修改的、支持相应接入的 FreeRTOS 教学工程。
本节描述实验步骤，不表示本笔记已执行这些操作。

### 实验 A：看懂 Ready 和 Running

创建两个有明确周期和有界工作量的任务，配置不同优先级。
让高优先级任务在低优先级任务就绪期间运行。
观察低优先级任务从 Ready 到 Running 的间隔，再解释它在等待谁。

先给每个任务定义周期、优先级、栈、输入输出和阻塞方式。
不要用无界忙等代替可控工作量，也不要直接在车辆控制任务里制造负载。

### 实验 B：区分墙钟耗时与 CPU 时间

在低优先级任务的一个有界处理阶段前后记录事件。
让高优先级任务在这个区间运行一次，比较用户区间时间与低优先级任务
实际执行片段之和。两者的差值应能从时间线上找到解释。

### 实验 C：检查一条消息链

给输入消息分配序号，记录输入、入队结果、消费开始、处理完成。
改变合法范围内的输入负载，观察端到端延迟、队列积压和丢弃计数。
不要只看平均处理时间，还要检查峰值与错误恢复路径。

## 19. 一次分析应该留下什么证据

- 固件版本或 Git 提交、编译配置，以及芯片和板卡版本。
- RTOS、SystemView 目标库、主机工具和探针版本。
- 时间戳源、频率、缓冲区与通道配置。
- 复现输入、负载条件、记录范围和预期时序要求。
- 原始记录、关键事件序号、时间范围和相关源码位置。
- 是否发生溢出，是否覆盖全部相关 ISR，统计采用什么口径。
- 已观察最大值、超期次数、正常与异常对照，以及硬件测量结果。

验收时至少区分三层：

1. 目标库编译通过，说明当前工程可以构建。
2. 记录完整且时间轴经校验，说明这份软件时序证据可用于分析。
3. 同步的总线或电压等测量，说明对应外部硬件行为确实发生。

这三层不能互相替代。本笔记完成的是概念、方法和文档整理，
没有替读者完成某个工程的移植或台架验收。

## 20. 自测与答案

### 任务 Ready 了 2 ms 才运行，能直接说算法需要 2 ms 吗？

不能。这 2 ms 是就绪后的启动等待。
算法 CPU 时间要看实际执行片段，完整业务耗时还要看业务边界。

### 两个函数标记相差 1 ms，函数就占用了 1 ms CPU 吗？

不一定。期间可能被中断、被任务抢占，或者阻塞等待资源。
先把墙钟耗时与 CPU 执行时间分开。

### 平均 CPU 负载只有 15%，能保证 1 ms 响应要求吗？

不能。还要检查关键窗口里的阻塞、抢占、突发和截止时间。

### 没有任务切换事件，能推断系统只有一个任务吗？

不能。也可能是跟踪接口没有接入、记录未开始或发生数据丢失。

### 把缓冲区扩大十倍，能解决持续带宽不足吗？

不能。它只能延后溢出，需要减少事件或提高实际消费能力。

### SystemView 显示已发出电磁阀请求，能证明阀已经动作吗？

不能。还需检查下游命令链、实际电压或电流，以及机械动作反馈。
